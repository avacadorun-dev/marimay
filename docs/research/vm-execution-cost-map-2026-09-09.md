# Общая модель затрат VM: следующий архитектурный шаг

Дата: 2026-09-09. Исходная ревизия: `9fb7523`.
Цель пользователя — паритет Marimay с Go/Rust на неизменных 32 workloads.
Bun остаётся промежуточным ориентиром для VM; он не заменяет эту цель.
Этот документ уточняет [существующий архитектурный маршрут](performance-parity-architecture-2026-09-09.md)
по прямым динамическим счётчикам. Он не объявляет новую оптимизацию выполненной.

## Почему мелкие изменения не закрывают разрыв

В [полной матрице](../implementation/evidence/cp42-vm-preparation-comprehensive-2026-09-09.md)
BFS занимает 5,72 s в VM и 70,16 ms в Marimay native. Устранённые ранее
8–9 ms подготовки полезны коротким задачам, но не объясняют этот разрыв.
Трёхсекундный CPU sample BFS поместил 1 980 из 2 528 отсчётов приложения
под `mmay_bytecode_run_hot`. При этом число точек входа в CLI не определяет
стоимость сотен миллионов операций внутри горячего цикла.

Новый диагностический проход насчитал **4 441 883 584 исходные VM-инструкции**
на всех 32 workloads. Их opcode-гистограммы и взвешенные профили блоков
полностью совпали в двух проходах. Все stdout/checksum/exit совпали с эталоном;
все 114 хешей исходников и harness остались прежними.
[Сырые данные](../implementation/evidence/cp42-vm-cost-map-2026-09-09.json).

## Охват общего механизма

«Общий набор» здесь — числа, bool, копирование значений, ветвления, доступ к
массивам, полям записей и состоянию enum. Это диагностическая классификация
операций, потенциально доступных общему compiler tier. Это ещё не доказательство
допустимости конкретной трассы и не доля CPU-времени. Все проверки типов,
границ, мутаций, ошибок и владения должны остаться в исполняемом контракте.

«Группировка» — отношение исходного числа инструкций к числу непрерывных
участков общего набора плюс отдельных остальных инструкций, если каждый
basic block возвращает управление диспетчеру. Это оценка количества dispatch,
а не обещание такого же ускорения wall time.

Отсюда следуют три общих механизма:

1. **Связанные вычислительные регионы.** В insertion, heap-sort, min-heap,
   BFS и Dijkstra общий набор покрывает 96–100% инструкций. Нужны произвольные
   проверенные CFG-регионы с переходами между скомпилированными блоками.
   Перечень распознаваемых алгоритмических shapes не должен расти вместо
   общего механизма. Возврат в C dispatcher после каждого блока сохраняет
   большую часть переключений: у BFS группировка только 3,67×, у Dijkstra 2,88×.
2. **Вызовы и транспорт значений.** DSU исполняет 15 002 065 вызовов,
   stack/queue — по 4 000 003, catalog-interface — 1 630 005. Min-heap делает
   91 233 489 `record_get`. Быстрый scalar-loop с холодной обработкой каждого
   поля и каждого вызова оставит системный барьер. Общему tier нужны прямые
   внутренние переходы для подходящих callees, компактные scalar slots и
   точное восстановление логических frames/roots/fuel при выходе.
3. **Подготовка и материализация runtime-значений.** В set-string-churn общий
   набор покрывает лишь 55,5% инструкций. Внутри отдельных строковых/Map/Set
   инструкций скрывается ещё работа runtime, которую счётчик dispatch не
   измеряет. Для native и коротких VM-задач остаются отдельные общие работы:
   borrowed text iteration, передача внутренних результатов без временных
   managed-объектов и разбор затрат первого source-run. Существующий разбор
   native-семейств остаётся применимым.

## Следующая реализация и проверка

Основной следующий владелец — **общий горячий CFG tier над verified execution
image D108**, с ограниченным бюджетом кода и платформенными executable-memory
owners. D019 допускает это только с независимым интерпретатором и прежней
семантикой. До включения фиксируются правила W^X, signed-runtime, resource
failure, очистки кода и доступности на Tier 1; внешний C compiler внутри
`--engine vm` не является реализацией этого tier.

Регионы строятся по opcode/type/CFG, без имён пакетов или workloads. План
хранит исходный pc/span и число логических инструкций. Fuel-проверки и side
exits должны точно воспроизводить разрешённый префикс, checked arithmetic,
ошибки массивов, logical call-depth, per-frame/shared fuel, GC и cleanup.
Неподдерживаемые регионы остаются в существующем интерпретаторе. Материализация
регистров и managed roots на границах — часть контракта, а не поздняя заплатка.

Проверять прототип следует на BFS, Dijkstra, min-heap и DSU, а изменения вызовов
— также на catalog-dotcall/interface. Кратный выигрыш на нескольких семействах
должен предшествовать большой интеграционной волне. После выбора реализации
нужны точные finite-fuel/alias/GC/failure tests и один полный приёмочный прогон
32×5 с 3 warmups и 11 samples. Локальные микрогипотезы сначала отсеиваются
диагностикой и короткими сравнительными пробами. Многократная полная матрица
после каждой мелкой правки не заменяет выбора общего механизма.

Эксперимент с двумя алиасами array-descriptor lookup отложен: корректность
прошла локальные Release 86/86 и ASan/UBSan 12/12, но его серия времени
пересеклась с чужим benchmark и не принята. Производственная реализация не
включена; этот документ не приписывает ей ускорение.

## Воспроизведение диагностического прохода

Инструмент предназначен для локального POSIX developer host с C17 toolchain
и соответствующим Release-архивом выбранной ревизии. Он создаёт отдельный
инструментированный executable. Production VM и corpus не редактируются.
В диагностической копии отключены D108 специализированные loops, чтобы
считать исходную инструкционную нагрузку, а не число fused dispatch. Поэтому
**время этой сборки нельзя использовать как benchmark**. Конечный managed-heap
лимит и все workload arguments сохраняются.

```sh
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release
cmake --build build/release -j4
python3 tools/performance/profile-vm-blocks.py \
  --benchmarks ../algorithm-benchmarks \
  --reference docs/implementation/evidence/cp42-vm-preparation-comprehensive-2026-09-09.json \
  --revision 9fb7523 --build build/release \
  --output build/vm-cost-map.json
```

Каждая исходная инструкция считается только после успешной горячей операции
или передачи холодной операции обычному dispatcher. Отдельно считаются входы
в блоки; сумма `visits × instructions` должна совпасть с opcode-гистограммой
на каждом успешном workload. Таблица ограничена 32 768 блоками; переполнение
отклоняет профиль. Статические типы/layouts нужны только классификатору,
результаты программы он не меняет. Проверяются stdout, stderr, exit и хеши
corpus до и после запуска. CLI допускает `--workload` для коротких проб;
полная опубликованная карта содержит все 32.

Эта карта не является новым результатом производительности или Tier 1 gate.
Её назначение — выбрать общее изменение до следующего цикла разработки.
