## Что я бы изменил в логике старого плана

**Последовательность приложений не равна технической зависимости.** Manifest
не зависит от завершения каждого замечания config; collection API для notes
не зависит от предварительного написания CSV-конвертера. Обязательный переход
по номерам заставляет поздно находить общие требования и повторно мигрировать
уже сделанные приложения. Предлагаю строить волны по используемым контрактам.

**Глобальная остановка на любом performance failure слишком широко связывает
работы.** Например, стоимость первого запуска нового native-файла на macOS
не запрещает заранее выяснить доступность Linux PMU или проверить контракт
стабильного удаления. Сам дефект продолжает блокировать соответствующую
приёмку и релиз. Ошибка общего native backend, напротив, затрагивает весь
native-кандидат: вокруг неё нельзя накапливать якобы принятые приложения.

**Поздняя подготовка окружений создаёт скрытый критический путь.** Наличие
физического измерительного Linux-хоста, доступных платформ, чистых install
images и внешних подтверждений N0 нужно выяснять в начале. Итоговая приёмка
действительно должна использовать финальный артефакт; подготовка её условий
от финального артефакта не зависит.

**Не каждое замечание требует нового языкового механизма.** Допустимые
завершения находки: исправление ошибки, небольшая общая операция библиотеки,
изменение прикладного дизайна либо обоснованное ограничение согласованного
scope. Например, два прохода для обнаружения версии JSON требуют измерения
и оценки API, но сами по себе не обосновывают DOM/reflection. Принятые пункты
CP42 о коллекциях, мутациях и Option сохраняются до отдельного решения.

**Нужна точка завершения оптимизации.** Формулировка «ещё медленнее Go» не
задаёт конечную работу. Нужны исходная причина, представитель класса нагрузок,
бюджет, ограничения по памяти/размеру кода и критерий отказа от прототипа.
Конкурентоспособность оценивается также по удобству обычного кода, диагностике,
скорости цикла разработки и воспроизводимой установке.

## Инженерная стратегия для оптимизирующего компилятора

Сохранять связку typed MIR → verifier → VM/C17 и общую семантику runtime.
[Архитектура](../implementation/compiler-architecture.md) уже предоставляет
разумную границу оптимизации; прочитанные источники не дают оснований сейчас
переписывать backend, вводить второй распределитель регистров или новый IR
ради самого наличия таких механизмов.

Для каждой нагрузки отдельно учитывать подготовку/компиляцию, запуск ОС,
построение входа, полезный цикл, коллекции и вывод. Не складывать перекрывающиеся
профили и не выдавать разность двух разных пробников за точное время слоя.
Если участок занимает 10% полного времени, даже полное его устранение даст
лишь около 1,11× общего ускорения. Выбор оптимизации должен учитывать этот предел.

| Слой | Что уже известно | Следующий ограниченный эксперимент |
|---|---|---|
| Алгоритм и storage | Устранены квадратичный traversal и частые полные перестройки после удаления; введён групповой индекс. | Проверить масштабирование и остаточные затраты новой версии на размерах/типах/операциях. Не начинать очередную замену таблицы без нового профиля. |
| Полный путь операции | До перестройки checked runtime доминировал у числового Map/Set; у rune существенен и путь обхода/передачи значений. На каждую операцию Option/Result не аллоцировались. | На свежей базе сравнить generated loop и тот же checked runtime, выделить проверки, descriptor dispatch, перенос cell/result и подготовку входа. Выбрать одну подтверждённую границу для изменения. |
| MIR → C17 → machine code | CP41 выявлял x86 code pressure. Emitter уже использует views и inline/outline. | Сопоставить живые значения, rooting, error/cleanup edges, размер функций и spills с optimization remarks и counters. Проверить сокращение живого состояния или изменение call policy на нескольких нагрузках. |
| Разработка и запуск | Native tests уже строятся одной сборкой; у свежего executable остаётся отдельная задержка первого запуска. | Разделить compiler preparation, host C compilation, runtime entry и pre-main startup; сравнить контрольные C17/Go/Rust программы в тех же условиях. |

Это опирается на [системный профиль](../implementation/evidence/cp42-collection-system-review-2026-09-07.md)
и [результат перестройки](../implementation/evidence/cp42-grouped-collections-2026-09-07.md).
В трёх локальных парных сериях она дала примерно 15% для frequency-map,
25% для unique-set и 16% для rune-frequency. Изолированный churn ускорился
сильно больше, но потребовал дополнительной памяти; маленькие операции местами
замедлились. Это полезный структурный результат, не всеобщее ускорение.

Есть конкретная проверяемая гипотеза для CP41: в
[c_emitter_emit.c](../../bootstrap/src/native/c_emitter_emit.c) порог
inline/outline использует общее число MIR-регистров (`32`), а record leaf
может получать forced inline. Число всех регистров не является числом
одновременно живых значений. Стоит проверить, объясняет ли эта эвристика
измеренные spills и рост кода, прежде чем добавлять следующие эвристики.
Это кандидат исследования, не доказанная причина и не заранее выбранный fix.

Typed specialization/сокращение внутреннего транспорта допустимы только там,
где сохраняются shape-sharing, alias/identity, GC, safepoints, checks и точные
failure/panic semantics. Массовая специализация может ускорить цикл и ухудшить
размер executable и время сборки. Новое `entry` API также нельзя добавлять
ради одного frequency benchmark без договора о lifetime и мутациях.

Для каждого прототипа: свежая база → одна гипотеза → одинаковые входы →
корректность/ресурсы → парные измерения → оставить или удалить. Прекратить
ветку, если эффект неотличим от шума, стоимость памяти/сборки неприемлема
или улучшение держится только на одном специальном случае. Уже принятый
невыполненный бюджет остаётся открытым и требует исправления либо явного
пересмотра контракта; отрицательный эксперимент сам его не закрывает.

## Один цикл для связанных языковых контрактов

Согласовать shallow copy, поиск позиции, стабильное удаление, результаты
мутаций и Option binding как одну семейную задачу с несколькими небольшими
реализациями. Начать с реальных выражений config и существующего notes:
сейчас `notes.add` вручную копирует массив, а `notes.remove` сдвигает элементы
исходного массива через alias. Это одновременно прикладная непоследовательность
и хороший сквозной тест общей модели коллекций.

Выход цикла: заранее описаны copy/alias, отсутствие элемента, неверный индекс,
стабильность порядка, инвалидирование итератора и material failure;
согласованы возвраты операций и область видимости Option binding;
checker/formatter/MIR/VM/native покрывают каждое изменение; config и notes
переходят на согласованный API в том же цикле. Ожидаемая ошибка не теряется
ради удаления `const _ = ...`. Обобщение должно иметь реальных потребителей,
а не создавать ещё одну обязательную библиотеку «на будущее».

Такой цикл объединяет проектирование и обратную связь. Он не означает один
огромный patch: решения, owners, focused tests и коммиты остаются отдельными.

| 1. Надёжная исходная точка | Сверить 42 строки с owners, тестами и платформами; выделить реальные дефекты. Разобрать открытый native CI failure до проверенного исправления/установленного результата на текущем SHA. Подготовить один общий драйвер прикладной приёмки из имеющихся config scripts. Выход: пригодная для дальнейших сравнений база и перечень доказанных пробелов. |
| 2. Общие контракты CLI | Совместно закончить collection/copy/remove/mutation/Option и необходимые error API; привести config и notes к согласованному дизайну. Выход: реальные программы используют итоговые выражения, семантика и ошибки проверены обоими движками; незакрытая платформенная latency явно остаётся в своём блокере. |

Выход: точные SHA/hashes и все требуемые результаты для заявленных платформ. Публикация остаётся отдельным действием пользователя. |

Волны приложений внутри третьего цикла:

| Семейство | Приложения | Что действительно переиспользуется |
|---|---|---|

С самого первого цикла идёт независимая подготовка: доступность Linux PMU,
перечень требуемых хостов и чистых установок, воспроизводимость упаковки,
перечень внешних свидетельств N0. Это граф зависимостей, а не требование
одновременно вести несколько semantic features или запускать несколько агентов.
Одновременно активна одна семейная реализация; CI и подготовка окружений
могут выполняться, пока не требуют её изменения.

## За счёт чего сокращается работа

- Общую механику трёх engine modes, process capture, fixture comparison,
  временных файлов и измерительных metadata делать один раз с десятью
  небольшими адаптерами. Собственные сценарии каждого приложения сохраняются.
  Версия harness фиксируется; приложения остаются самостоятельными и работают
  без путей в соседние checkout. Новая package infrastructure не нужна.
- Семантику общих API проектировать на нескольких потребителях сразу.
  Это уменьшает повторные миграции, а не просто число строк прикладного кода.
- Проверку одного требования связывать с несколькими строками matrix через
  его ID, когда она действительно их покрывает. Не писать заново одно и то же
  доказательство для checker, VM, native и std; различия engines всё равно тестируются.
- Общие CI, fuzz, sanitizer и install результаты собирать в manifest кандидата
  и ссылаться на них из CP-карточек. Не переносить старое прохождение на новый SHA.
- Различать developer-loop проверки и выпускную сверку. Каждый semantic patch
  сохраняет обязательные local gates, focused tests и настроенный CI на push.
  Полная финальная сверка идёт на замороженном кандидате; изменение кандидата
  инвалидирует затронутое доказательство. Сокращение проверок не предлагается.
  В частности, обязательную Tier 1 приёмку CP42 нельзя отложить за закрытие
  CP41: она проходит на CP42-ревизии, а последующие backend-изменения требуют
  проверки итогового артефакта. Переиспользуются инфраструктура и записи
  результатов, не утверждение, что прежний бинарник проверил новый.

Это измеримое сокращение повторяемых операций: одна реализация harness,
одна согласованная модель API, один пакет evidence кандидата. Сколько это
сэкономит календарного времени, зависит прежде всего от native CI-дефекта,
startup, x86 результата и доступности платформ. Число карточек не является
ни оценкой трудозатрат, ни процентом готовности.

## Какие правила требуют отдельного решения

| Нынешнее правило | Рекомендация | Что сохраняется до принятия |
|---|---|---|
| Десять утилит строго в порядке таблицы; любой performance failure останавливает переход. | Принять волны по зависимостям и блокировать связанные с дефектом приёмки, оставляя независимую подготовку возможной. | Все десять утилит, неизменённые workloads и бюджеты; старый порядок действует. |
| CP41 требует заранее заданных 15%/10% улучшений и 20% уменьшения stack-addressed operations. | Сначала подтвердить актуальность исходной проблемы на свежем baseline. Если она сохранилась — выполнить критерии. Если исчезла или изменилась — представить измеренное основание для нового accepted decision. | Нынешние числа обязательны; уже сделанные оптимизации не закрывают CP41 автоматически. |
| Подготовка CP39 читается как работа только после CP41. | Разрешить заранее проверять установочную инфраструктуру; закрывать CP39 только на итоговом кандидате. | Последовательность верификации CP42 → CP41 → CP39 → CP40. |
| D057 требует пять платформ; формулировки CLI0 также используют «заявленные хосты». | До оценки срока явно согласовать точный CLI0 platform scope с D057 и release claim. Базовый расчёт сохраняет существующее обязательство пяти платформ. | Linux x86_64/arm64, macOS arm64/x86_64, Windows x86_64 не исчезают из gate из-за недоступности локально. |
| N0 объединяет необходимые для выпуска identity evidence и пространства будущей registry/ecosystem. | Проверить продуктовую необходимость каждой строки именно для CLI0; будущие namespaces можно предлагать перенести только с поправкой решения и спецификации. | N0 остаётся блокером; этот анализ не является правовой оценкой или подтверждением контроля. |

Основания последней сверки scope: [D057](../design/decisions.md#d057-checkpoint-21-uses-a-linux-reference-baseline-before-public-alpha-tier-1-closure),
[граница CLI0](../implementation/roadmap.md#cli0-boundary),
[N0](../design/naming-audit.md), [нормативная identity](../spec/toolchain.md).
Это выявленная необходимость согласовать объём, а не молчаливый выбор
удобного прочтения. Сокращать десять приложений или заявлять готовность на одной
локальной машине в рекомендуемый маршрут не входит.

## Конкурентоспособность и момент обратной связи

Для bounded CLI полезная цель — обычный безопасный код без ручных codec/copy
ритуалов, предсказуемые ошибки и ресурсы, быстрые проверки/тесты, достойная
производительность типичных задач и понятная установка. Скорость алгоритмов
остаётся важной, но проход одной таблицы benchmark не доказывает всё это.

Предлагаю после стабилизации API подготовить небольшой частный usability
сценарий для 2–3 внешних разработчиков: установить, написать фильтр, исправить
ошибку типов, обработать JSON и запустить тесты. Это ранняя проверка понятности
CLI, а не замена обязательного E0 с его I6/concurrency scope и не новый
автоматический release gate. Контакт с людьми требует отдельного поручения.

## Книга и происхождение идей

Перегруппировка roadmap получена из зависимостей, исходников и evidence этого
проекта. Она не приписывается книге Владимирова. Ранее применённые идеи:
сохраняемый прогресс обхода — печатные **158–160, 168–169**, PDF
**159–161, 169–170**; ограничения выноса generation checks — печатные
**173–174**, PDF **174–175**. Точные применения и границы результата есть в
[журнале книги](vladimirov-optimizing-compilers-2026-09-07.md).
Новый эксперимент с inline/outline или liveness в рамках этого анализа
не выполнялся; новая книжная оптимизация не заявляется.

Ближайший предлагаемый результат после принятия маршрута — сверенная карта
остатка работ и пригодная CI-база, затем один сквозной цикл общих API с config
и notes. Это даёт проверяемую точку прогресса без ожидания завершения всех
десяти приложений и без преждевременного объявления альфы готовой.
