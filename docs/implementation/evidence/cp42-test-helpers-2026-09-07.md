# CP42: expect в обычных тестовых помощниках

Локальная проверка D093 на 2026-09-07, macOS arm64 / Apple M2 / AppleClang 21.
База `82e3513a591bdd19c07604b842ded8b801a1a720` с предыдущими рабочими изменениями
D089–D092. [Сырые данные, исходники и хеши](cp42-test-helpers-2026-09-07.json).
CP42, CLI0 и полная платформенная приёмка остаются открытыми.

## Причина и изменение

Обычная `fn same(...)` внутри `_test.my` с `expect.equal(...)` отвергалась
`R0007`, даже если вызывалась из `@test`. Контекст ожиданий определялся только
атрибутом текущей функции. [D093](../../design/decisions.md#d093-expectations-in-ordinary-test-file-helpers)
связывает эту возможность с определяющим `_test.my`: helper не требует
аннотации или дополнительного параметра. Производственный `.my` не получает
`expect` от вызова из теста. Состав обнаруживаемых `@test`/`@fuzz`, изоляция,
лимиты, shadowing и обычное исполнение вызовов сохранены.

В `checker_declaration_functions.c` меняется источник test-context;
`checker_expr_test.c` сообщает актуальную причину запрета. Новых runtime/MIR
операций или обходов в backend нет. Обобщённые помощники проверяются по своему
определяющему AST при специализации.

## Проверки

- Focused checker выполняет вложенные helper-вызовы, проверяет только два
  аннотированных test entry среди четырёх функций, точный G4004/message/symbol/
  span и каждый достижимый индекс отказа checker-аллокаций. После teardown
  `live_allocations == 0` и `live_bytes == 0`.
- Независимый `test_native_test_helpers.c` проверяет helper-позицию и оба
  call frame в bytecode VM и диагностическом C17 entry при `-O0`/`-O2`.
  Этот focused owner зарегистрирован в CP42 ровно один раз.
- Публичный пакет: три теста с generic int/string, вызовами между `_test.my`,
  захватом Unicode-вывода и `defer`/общим массивом. Неаннотированный helper
  с ложным ожиданием не запускается как тест. Production `main` отдельно
  выполняется в VM и Debug/Release native.
- Намеренно падающий helper даёт побайтно одинаковый отчёт в VM/native/both:
  G4004, один failed и один passed. Производственная функция с ожиданием
  одинаково отвергается `check`/`run`/`build`/`test` с R0007 и без артефакта.
- Полный Release: **71/71**, 244,75 с, включая configuration-specific
  source packaging. Выбранные checker/CP42/CLI-test/public: Debug **4/4**,
  ASan+UBSan **4/4**. В первом focused driver была неверно ожидаемая колонка
  диагностики (20 вместо 21); после исправления driver повторно прошёл.
- Linux amd64 ASan+UBSan+LSan: checker и CP42 **2/2**, 665,89 с; тот же
  публичный driver также прошёл. Ubuntu 24.04 / Clang 18.1.3 в существующем
  контейнере под эмуляцией на M2, без сети. Это дополнительная регрессия,
  не нативная Tier 1 площадка и не CI отправленного кандидата.

Проверенный Release compiler SHA-256:
`2790d7d58c8df17cc34b79990f313d58234a64212153aeec2ffa820a67fd0d3e`.
Снимок и source hashes сохранены до последующей работы над D094.

## Приложение и оставшийся finding

Внешний `marimay-config/main_test.my` использует `expect.equal` внутри
помощника `rejected` вместо ручного сравнения и panic. `fmt --check`,
`check --all-targets`, семь тестов в обоих движках и 32 процессных случая
× VM/Debug native/Release native прошли. Дополнительные atomic/capability/
broken-pipe проверки сохранены. 54,45 с — время проверки под другой нагрузкой,
не latency baseline. Репозиторий приложения остаётся без коммита/remote.

Выполнение сохраняет точные panic spans, но нынешний краткий CLI test report
печатает только код и сообщение panic. Человек пока не видит файл/строку
помощника; это отдельно зарегистрированный E09, не исправление в D093 и не
основание объявлять тестовую диагностику полностью принятой.

Идеи книги Владимирова здесь не применялись. Основание — воспроизводитель E02
и явный контракт определения тестового кода; книжные страницы этому изменению
не приписываются.
