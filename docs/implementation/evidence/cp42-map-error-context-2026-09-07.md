# CP42: точный контекст ошибки для mapError

Локальная проверка D094 на 2026-09-07, macOS arm64 / Apple M2 / AppleClang 21.
База `82e3513a591bdd19c07604b842ded8b801a1a720` с рабочими D089–D093.
[Исходные воспроизводители, хеши и логи](cp42-map-error-context-2026-09-07.json).
CP42, CLI0 и полная Tier 1 приёмка остаются открытыми.

## Причина и изменение

В реальном `marimay-config` выражение `cli.parse(...).mapError(cli.message)?`
отвергалось T0002: разрешение mapper не использовало известный входной тип
ошибки для выбора существующей nominal-first-parameter перегрузки. Лямбда
без аннотации результата тоже отвергалась: `?` не передавал контекст ошибки.
Работал только обход `(error): string => cli.message(error)`.

[D094](../../design/decisions.md#d094-exact-error-context-for-result-mappers)
задаёт выбор видимого unary mapper по точному входному E, с обычными правилами
импортов, переименования и затенения. Только прямой операнд `?`, включая
прозрачные скобки, получает F от окружающего `Result<U,F>`. Успешный тип T
принадлежит receiver и не обязан совпадать с U. Контекст отмечен идентичностью
AST; вложенный `?` сохраняет и восстанавливает его на всех выходах. Вложенные
mapper-выражения не получают контекст соседнего вызова.

`checker_expr_map_error.c` использует существующий callable resolver;
`checker_expr_try.c` передаёт ограниченный контекст через обычную проверку
выражения. Query просматривает только стабильные объявления prelude и не
выделяет импортированный enum view для неподходящего типа. VM/native не
выполняют дополнительный вывод типов и потребляют прежний typed MIR.

Заодно исправлены два нарушения существующей типизации: локальное имя mapper
или namespace действительно затеняет импорт; пользовательский enum с двумя
параметрами и похожими вариантами не становится Result. Baseline принимал
такие программы. Теперь они отвергаются на source boundary, до исполнения.

## Проверки

- Checker: локальные/qualified/renamed перегрузки, generic enum-конструктор,
  лямбда без аннотации, разные T/U, скобки, восстановление вложенного `?`,
  отрицательные контексты и затенение. Oracle проверяет результат, MIR verifier
  — все функции. Перебраны все достижимые индексы отказа аллокаций checker
  и импортного графа; после teardown оба счётчика живой памяти равны нулю.
- Публичный пакет: пять исходных тестов в VM/native, счётчики однократного
  receiver и вызова mapper только на Err, void payload, generic constructor,
  вложенная propagation. `fmt --check`, `check --all-targets`, VM main и
  Debug/Release native main проходят. Шесть отрицательных пакетов дают
  одинаковый T0002 в check/run/build и не создают исполняемый артефакт.
- Выбранные Release **3/3**, 4,68 с; Debug **3/3**, 9,23 с;
  ASan+UBSan **3/3**, 12,78 с. Полный финальный `ctest --preset release`
  **72/72**, 249,52 с, включая configuration-specific packaging.
- Linux amd64 / Ubuntu 24.04 / Clang 18.1.3: checker **1/1**, 43,28 с,
  и тот же публичный driver прошли с ASan+UBSan+LSan. Существующий образ,
  сеть отключена, M2-эмуляция; это не нативная Tier 1 площадка и не remote CI.
- Девять repository gates проверены; результаты до/после регистрации отчёта
  сохранены в JSON. Повторная упаковка после регистрации проверяет комплектность
  документации исходного архива. Нового синтаксиса или формата bytecode нет.

Проверенный compiler SHA-256:
`eee144223830b3b7d3de21cd268d4f74cd2b181288c16ee8978dccaf0e3f439a`.
Снимок source/app hashes сделан перед последующим расширением файловой
приёмки приложения; новые app harness и его результат учитываются отдельно.

Первая реализация передавала весь ожидаемый Result и неверно связывала T/U;
разделённый error-only контекст исправил это до финальной проверки. Первый
import alias тест выявил неверный выбор общего resolver вместо free-call
resolver. Исходные неудачные smoke/driver логи сохранены, успешными не считаются.

## Реальное приложение

`marimay-config/command/options.my` теперь использует
`cli.parse(parser(), arguments).mapError(cli.message)?`. Пройдены обычный
installed `doctor`, fmt/check, семь исходных тестов в обоих движках и прежние
32 процессных сценария × VM/Debug native/Release native; atomic/capability/
broken-pipe проверки сохранены. Финальный прогон занял 61,12 с под нагрузкой,
это не latency baseline. E03 локально исправлен; приложение без коммита/remote.

Последующий отдельный POSIX harness приложения прошёл **23 случая × 3 движка**
на macOS: реальные mode-bit отказы чтения/прохода/записи с независимой
проверкой ОС, статические ссылки в конечном/родительском компоненте,
внешние и оборванные targets, каталоги/FIFO, Unicode/пробелы, сохранность
файлов и отсутствие временных остатков. Первая fixture находилась под source
root и вызывала нормативный K0004 при discovery; данные вынесены за исходный
модуль. Это не проверка конкурентных namespace races. Хеш harness и сырые
наблюдения сохранены отдельно от исходного снимка D094 в JSON. Тот же
harness прошёл 23 × 3 на Linux amd64 под M2-эмуляцией, с непривилегированным
UID 501, ASan+UBSan+LSan и отключённой сетью.

Идеи книги Владимирова в D094 не применялись: изменение основано на
воспроизводителе E03 и контракте типов. Книжные страницы ему не приписываются.
