# CP42: групповой индекс и перестройка Map/Set — 2026-09-07

После [системного разбора](cp42-collection-system-review-2026-09-07.md)
изменено устройство общего индекса Map/Set и политика перестройки ordered
storage. D090/D091 реализованы в основном runtime; обычный `mmay` пересобран.
CP42 и CLI0 остаются открыты.

[Сырые данные](cp42-grouped-collections-2026-09-07.json) содержат все финальные
парные samples/warmups, первоначальные прототипы, 846 проверочных запусков,
исходники диагностик, hashes compiler/runtime/owners, отчёт неизменённого
expanded runner и логи приёмки. База — `82e3513` с D089 в рабочем дереве;
владельцы Map/Set до этого изменения совпадали с базовой ревизией.
Внешние benchmark sources и прежние latest reports не менялись.

## Выбранная реализация

**D090.** Ordered entry storage сохраняет порядок вставки. В индекс добавлен
один control byte на bucket: семь старших битов полного SipHash-2-4 либо
метка empty/deleted. Семь зеркальных байтов позволяют читать группу через
конец таблицы. Большие индексы фильтруют восемь позиций сразу; минимальный
индекс из восьми позиций просматривает отдельные метки. Первый прототип
группировал и маленькие таблицы, что дало заметные регрессии; он не выбран.

Линейная последовательность пробирования, первое доступное удалённое место,
75%-ный load factor, полное сравнение hash/key и строковое/номинальное равенство
сохранены. Reference-кандидат можно отвергнуть и продолжить ту же ограниченную
последовательность. Групповой фильтр допускает лишних кандидатов, но не доказывает
равенство ключей. Каждое чтение записи проверяет индекс, storage и active state;
публичные операции проверяют полные managed handles. Lookup не является аудитом
всех корзин, отсеянных приватными метками; это уточнение явно принято в D090.

**D091.** Матрица выявила проблему политики хранения: при заполненном entry
storage единственное удаление заставляло следующую вставку копировать все
записи и перестраивать индекс. Теперь уплотнение при прежнем резерве выбирается,
когда живо не более половины записей; иначе резерв растёт геометрически.
Перестройка распределяется на много последующих операций. После удаления
последнего элемента append position и индекс сбрасываются на месте, и пустой
резерв используется снова без выделения памяти.

SipHash-2-4, оба seed, виды ключей, API, D089 cursors и прежние ordinal
bytecode-операции сохранены. Метки находятся в прежней bucket allocation:
новых полей объекта, roots или дополнительных allocation calls нет.
Размеры проверяются и учитываются; replacement buffers публикуются после
успешного выделения и перестройки. Неудачный put сохраняет состояние перед put,
включая уже совершившийся предыдущий remove.

Владельцы: `managed_map_probe.c` и узкий `managed_map_index_internal.h`;
`managed_map_storage.c` планирует, учитывает и публикует storage;
`managed_map.c` поддерживает индекс при мутациях. Set использует тот же путь.

## Исходные counting workloads

Одинаковый generated C связан с сохранённым baseline и финальным Release
runtime. Эффективная оптимизация обоих runtime и C-программ — `-O2`;
LTO и ослабление floating-point правил не добавлялись. Три парные серии:
три warmup и одиннадцать samples, чередование порядка, сохранение всех
измерений и проверка точного stdout/status. Часы полного процесса включают
создание входа, подсчёт, checksum и teardown.

| Нагрузка | Baseline, диапазон медиан 3 серий, мс | Финал, мс | Улучшение в парных сериях |
|---|---:|---:|---:|
| frequency-map | 37,944–37,996 | 32,186–32,528 | 14,4–15,2% |
| unique-set | 35,396–35,528 | 26,611–26,677 | 24,8–24,9% |
| rune-frequency | 25,496–25,892 | 21,512–21,743 | 15,6–16,0% |

Отдельный прямой C-пробник тех же checked API, с подготовкой вне таймера,
даёт соответственно 29,565–29,683 → 24,506–24,581 мс,
30,166–30,251 → 21,201–21,253 мс и 11,193–11,354 → 10,664–10,678 мс.
Эти границы нельзя складывать или вычитать как точное разложение всего native
цикла: инструкции и обращения к памяти взаимодействуют по-разному.

После парных серий неизменённый пользовательский `benchmarks/run.py --expanded`
заново собрал все исходные программы и проверил контрольные суммы:

|---|---:|---:|---:|
| frequency-map | 32,40 | 13,79 | 23,47 |
| unique-set | 26,82 | 15,93 | 18,38 |
| rune-frequency | 21,69 | 5,60 | 5,89 |

Все одиннадцать workloads и данные toolchains находятся в JSON. Этот прогон
показывает текущую установленную версию. Разрыв, особенно у rune, остаётся.

Условия: Apple M2, macOS arm64, интерактивный host **от батареи**. Собственные
тяжёлые проверки были завершены; диагностический Linux-контейнер приостановлен
на интервал измерений 10:11:46–10:13:12 UTC и затем возобновлён. `caffeinate`
удерживал host от сна, параметры системы не менялись. Это локальное парное
свидетельство, не dedicated/mains-powered Tier 1 performance acceptance.

## Размеры, операции и цена резервирования

Первичная матрица: 282 сочетания Map/Set с raw, string и record keys;
0, 1, 4, 8, 12, 16, 64, 4096, 20001 и 65536 элементов; hits, misses, updates,
insert и churn. Финальные 846 проверочных запусков повторили значения и порядок
baseline. Часть шла одновременно с correctness jobs; их время не используется.

Финальная парная матрица на 1, 12 и 4096 ключах имеет три warmup и одиннадцать
samples на каждую сторону. Для churn на 4096 ключах — 10000 remove/reinsert
пар; для остальных строк — 100000 операций:

| 4096 ключей, 10000 замен | Baseline, мс | Финал, мс |
|---|---:|---:|
| raw Map | 204,263 | 0,826 |
| raw Set | 192,649 | 0,815 |
| string Map | 220,501 | 1,450 |
| string Set | 206,386 | 1,462 |
| record Map | 220,507 | 2,016 |
| record Set | 205,046 | 2,041 |

Это изолированные runtime replacements, не ускорение всего приложения в
100–250 раз. На 100000 замен при 4096 ключах число storage allocations
сократилось с 200000 до 50. При одном элементе — с 50000 до нуля; заметного
выигрыша времени там нет. Некоторые маленькие read/update случаи медленнее
на величину до 6,8%; общего ускорения всех операций нет.

| Retained managed/storage bytes | Baseline | Финал |
|---|---:|---:|
| frequency-map, без удалений | 197000 | 205199 |
| unique-set, без удалений | 1048968 | 1081743 |
| rune-frequency, без удалений | 1032 | 1055 |
| raw Map, 4096 ключей после churn | 197000 | 336271 |
| raw Set, 4096 ключей после churn | 164232 | 270735 |

Метки добавляют `capacity + 7` байтов непустому индексу. Амортизация перестройки
после редких удалений требует большего резерва записей; память для churn
заметно выше. D055 учитывает именно её, поэтому точная граница budget failure
может измениться. Это явная цена выбранной политики.

## Проверки

Независимый scalar model сравнивает 1423360 synthetic probe cases и reference
resumptions: несколько capacities, wraparound, collisions, tombstones и ложные
кандидаты меток. Отдельно проверяются недопустимые capacities, отсутствующее
или неактивное storage, индексы и противоречивые просмотренные markers.

Storage tests независимо проверяют control encoding и зеркальный хвост при
росте, удалении, уплотнении, clear и отказах. Все шесть raw/reference layouts
проходят точные byte boundaries и каждую достижимую allocation-failure
позицию. Churn owner проверяет независимую ротацию insertion order, ограничение
allocations, GC и failure-atomic put после remove. Каждый полный teardown
требует `live_allocations == 0` и `live_bytes == 0`.

| Приёмка | Результат |
|---|---|
| macOS полный Release | 68/68, 282,82 с |
| macOS focused runtime / CP36 / public corpus, Release | 3/3, 30,57 с |
| macOS те же проверки, Debug | 3/3, 45,58 с |
| macOS те же проверки, ASan + UBSan | 3/3, 65,52 с |
| Linux amd64, ASan + UBSan + LSan | runtime и CP36 прошли |
| Linux публичная приёмка | fmt/check, VM/native 17 tests, Release build/run прошли |
| Внешний marimay-config | 32 exact-parity cases × 3 engines; atomic/denied/broken-pipe прошли |
| Обычный PATH | `mmay doctor --json`: compiler и оба runtime согласованы |
| Архитектура, C memory policy, generated, roadmap/docs/spec/examples/syntax, release contract | все gates прошли |
| Финальные distribution / relocation / release-contract tests | 3/3, 21,38 с |

Linux — Ubuntu 24.04 / Clang 18.1.3 под эмуляцией на M2, существующий образ,
source read-only, network disabled, `detect_leaks=1:halt_on_error=1`.
Его durations включают паузу и не являются latency evidence. Это не замена
физической Tier 1/CI-приёмки. Debug/ASan повторены по затронутым владельцам;
прежние полные D089 suites и fuzz campaign не выдаются за повторную проверку
D090/D091. Отсутствие всех возможных утечек не утверждается.

## Источники идей и следующий шаг

Групповые метки мотивированы собственным профилем и первичным
[описанием Swiss Tables от Abseil](https://abseil.io/about/design/swisstables).
Реализация C17 сохраняет ordered storage и линейную последовательность позиций.
Политика перестройки получена из воспроизведённого allocation/churn поведения.
Эти две идеи не приписываются книге Владимирова.

Предыдущее применение книги — сохраняемый прогресс обхода: печатные 158–160
и 168–169 / PDF 159–161 и 169–170. Детали и ограничения есть в
[журнале книги](../../research/vladimirov-optimizing-compilers-2026-09-07.md).

Локализованные проблемы индекса и частоты перестроек имеют реализацию и
приёмку. Остаются полный typed operation/array-rune путь, прочая CP42
эргономика и приложения; CP41 должен получить эти артефакты при анализе
скорости исполнения. Продуктовые gates этим отчётом не повышаются.
